## 结论

Opus 5 的服务入口方向仍成立，但不能按“入口 CRUD 页面已完成”验收。入口页面、策略执行闭环和路由可视化仍有实质缺口。现行方案明确为 **failover、race、load_balance、shadow**，默认 failover。用户随后确认多入口并排比较同时覆盖对外入口与直接上游入口：公开入口部分可复用现有单次调用 API；直接上游部分必须补充受管理权限约束的 daemon 调用能力，不能仅靠公开模型列表完成。布局与状态管理可并行推进，完整功能依赖目标类型及执行契约。

本轮已排除“仅仅刷新或重启 Demo 就能解决”的解释：5173 的三个模块 source map 与磁盘一致，新编译内核重启后仍复现入口缺口。Tauri 壳确实较旧，但此次复用已有 daemon，并加载与当前 ui/dist 一致的页面资源。

## 依赖与推进顺序

1. **确认运行基线（本轮已完成）：**5173/Tauri 实测与新内核隔离复现，记录来源，避免把重启当实现。
2. **完成入口数据与执行闭环：**持久化、入口 CRUD/路由原子更新、实时生效，接通 `Registry::invoke`；策略只对已实现部分开放。
3. **完成入口页面与路由管理：**按现行计划的卡片和编辑流程实现，接真实 API；同时更新路由图以反映新模型。
4. **验证请求与可观测性：**核对实际策略行为、错误路径、SSE/日志事件和配置热更新。
5. **扩展两类入口演练：**公开入口部分复用 `/v1/models` 和 `/v1/systemone`；直接上游部分接入新的受管理权限约束的后端测试能力，不能把 provider/model 自动当作公开 model。布局和独立结果状态可与步骤2–3并行，完整联调在契约与执行接通后进行。详细方案见 [PLAYGROUND-COMPARISON-PLAN.md](design/PLAYGROUND-COMPARISON-PLAN.md)。

                |
       +--------+---------+
       |                  |
  入口数据/真实执行    图形交互/多入口比较
  CRUD/路由/策略      共享输入/全宽结果
       |                  |
       +---------+--------+

策略实现先以 failover 打通闭环，再逐项接入 race/load_balance/shadow；这不删减已批准范围。负载均衡的权重定义、race 有效胜出条件及取消、shadow 生命周期都应有明确验收行为。图形编辑中应完整恢复边的 priority/sticky/on_error，不能只恢复一根外观相同的线。
