# 上游类别与协议兼容矩阵

> 详化 `02-` v2.1 的 5 类上游分类。本文档是配置 `~/.jev-switch/config.toml` 与 `Upstream::capabilities()` 的依据。
>
> 实测依据：本仓库同级的 `jev-decision-lab/runs/integrated-benchmark-data.json`（5 provider × 4 version × 12 题）+ `life-series-benchmark/results/`（80 篇 × 14 标签）。

---

## 一、5 类上游完整定义（v2.1）

| # | 类别 | 协议形态 | 部署 | 代表实现 | 核心差异点 |
|---|---|---|---|---|---|
| **C1** | TypeSafe 云端官方 | Jev 原生 | 云 | `api.typesafe.ai/v1/systemone` | 标准 reference |
| **C2** | 第三方 Jev 透传网关 | Jev 变体 | 云 | OpenRouter、Vercel AI Gateway | 协议字段差异 |
| **C3** | LLM-Jev broker（嵌入） | LLM 协议 + 翻译 | Jev-Switch 进程内 | jev-life broker / 自实现 | prompt + JSON |
| **C4** | 本地独立 Jev 兼容服务 | Jev 原生 | 独立 HTTP 服务 | LLM2Jev / LM Studio jev-api / sys1 | 与 C1/C5 同协议 |
| **C5** | 本地真 Jev 模型 | Jev 原生 | 本地推理 | Laya / sys1 candle | 最快（30ms） |

**为什么 C3 和 C4 必须分开**：

- **C3 broker 嵌进程内**：用户填 LLM endpoint，Jev-Switch 用 prompt + JSON/tool calling 在自己进程内翻译。优点是部署简单（单进程）。缺点是 broker 配置跟着 Jev-Switch 走，密钥共享。
- **C4 独立 HTTP 服务**：LLM2Jev / LM Studio jev-api / sys1 各自起一个进程，暴露 `POST /v1/systemone`。Jev-Switch 把它们当 C1/C5 一样调用，**不做翻译**。优点是服务可独立升级、独立部署。缺点是用户要额外启进程。

两者**可同时配**：C3 跑本地 Qwen + JSON，C4 跑 LLM2Jev + prefill-only。

## 二、协议字段详细矩阵

### 2.1 Jev 标准协议（TypeSafe 官方）

`POST /v1/systemone` 请求体：

```json
{
  "model": "jev-latest",
  "state": "any text or object",
  "questions": {
    "q1": {
      "type": "choice",          // "choice" | "score" | "noul"
      "instructions": "...",
      "criteria": { "A": "...", "B": "..." }  // or [..] for score
    }
  }
}
```

响应：

```json
{
  "model": "jev-1.13.0",
  "answers": {
    "q1": {
      "type": "choice",
      "choice": "A",
      "probabilities": { "A": 0.7, "B": 0.3 },
      "confidence": 0.7
    }
  },
  "usage": { "input_tokens": 42, "output_tokens": 0 }
}
```

### 2.2 实测 5 类上游的字段支持

| 字段 | C1 TypeSafe | C2 OpenRouter | C2 Vercel | C3 broker | C4 LLM2Jev | C4 LM jev-api | C5 Laya |
|---|---|---|---|---|---|---|---|
| `type: choice` | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ |
| `type: score` | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ |
| `type: noul` | ✅ | ✅ | **`boolean` 替代** | ✅ | ✅ | ✅ | ✅ |
| `choice` (answer) | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ |
| `score` (answer) | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ |
| `noul` (answer) | ✅ | ✅ | **`boolean` (P=0.95/0.05)** | ✅ | ✅ | ✅ | ✅ |
| `probabilities` | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ |
| `confidence` | ✅ | ✅ | ❌ **缺失** | ✅ | ✅ | ✅ | ✅ |
| `usage.input_tokens` | ✅ | ✅ | ❌ | ❌ | ❌ | ❌ | ❌（估算） |
| `usage.output_tokens` | ✅ | ✅ | ❌ | ❌ | ❌ | ❌ | ❌ |

**关键差异**：

- **C2 Vercel `type: noul` 实际是 `boolean`**：Jev 协议标准 spec 是 `choice/score/boolean`（Vercel 适配版），**没有 `noul`**。需要在 Jev-Switch 做翻译层。
- **C2 Vercel 缺 `confidence`**：从 `probabilities` 推断（`max(probs)`）作为缺失字段的回退。
- **C3 broker 缺 `usage`**：LLM token 走的是 LLM 协议的 `usage.prompt_tokens/completion_tokens`，需要翻译。

### 2.3 capability 收敛（capabilitiesOf 模式）

借鉴 jev-life 的 `CAPABILITIES` 表设计，按**协议族**索引而不是按厂商：

```rust
struct UpstreamCapabilities {
    // 该上游收哪些 question type
    supports_question_types: &'static [QuestionType],
    // 该上游能否给 confidence
    supports_confidence: bool,
    // 该上游能否给 usage
    supports_usage: bool,
    // 该上游 noul 是 noul 还是 boolean（Vercel 适配）
    noul_discriminator: NoulDiscriminator,  // Noul | Boolean
    // 该上游重试策略
    retryable_status: &'static [u16],
}

const CAPABILITIES: &[(&str, UpstreamCapabilities)] = &[
    ("typesafe",        UpstreamCapabilities { supports_question_types: &[Choice, Score, Noul], supports_confidence: true,  supports_usage: true,  noul_discriminator: Noul,     retryable_status: &[408, 429, 500, 502, 503, 504] }),
    ("openrouter",      UpstreamCapabilities { supports_question_types: &[Choice, Score, Noul], supports_confidence: true,  supports_usage: true,  noul_discriminator: Noul,     retryable_status: &[408, 429, 500, 502, 503, 504] }),
    ("vercel",          UpstreamCapabilities { supports_question_types: &[Choice, Score, Boolean], supports_confidence: false, supports_usage: false, noul_discriminator: Boolean,  retryable_status: &[408, 429, 500, 502, 503, 504] }),
    ("laya",            UpstreamCapabilities { supports_question_types: &[Choice, Score, Noul], supports_confidence: true,  supports_usage: false, noul_discriminator: Noul,     retryable_status: &[0] }),  // 本地不需要 retry
    ("llm2jev",         UpstreamCapabilities { supports_question_types: &[Choice, Score, Noul], supports_confidence: true,  supports_usage: false, noul_discriminator: Noul,     retryable_status: &[0] }),
    ("lm_studio_jev",   UpstreamCapabilities { supports_question_types: &[Choice, Score, Noul], supports_confidence: true,  supports_usage: false, noul_discriminator: Noul,     retryable_status: &[0] }),
    ("sys1",            UpstreamCapabilities { supports_question_types: &[Choice, Score, Noul], supports_confidence: true,  supports_usage: false, noul_discriminator: Noul,     retryable_status: &[0] }),
];
```

### 2.4 noul→boolean 翻译层（Vercel 适配）

Vercel AI Gateway 的 `boolean` 类型与 Jev 标准的 `noul` 语义对齐：

| Jev noul (问题) | Vercel boolean (问题) | 翻译 |
|---|---|---|
| `type: noul`, criteria `{true: "是", false: "否"}` | `type: boolean`, criteria `{true: "是", false: "否"}` | **直接重命名 type** |
| answer `{noul: 0.7}` | answer `{boolean: true}` (概率 > 0.5 = true) | **0.7 → true**；< 0.5 → false |

**Vercel 概率损失**：boolean 丢掉原始概率（只保留 true/false）。补救：从 `criteria` 与 `boolean` 派生 `probabilities`（true → 0.7, false → 0.3）。

```rust
// Vercel boolean → Jev noul 翻译
fn vercel_boolean_to_noul(vercel_ans: &VercelBooleanAnswer) -> JevNoulAnswer {
    let probability = if vercel_ans.boolean { 0.95 } else { 0.05 };
    JevNoulAnswer {
        noul: probability,
        // 从 boolean 推断 probabilities（Vercel 不给原始概率）
        probabilities: { "true": probability, "false": 1.0 - probability },
    }
}

// Jev noul 问题 → Vercel boolean 问题
fn jev_noul_to_vercel_boolean(q: &JevNoulQuestion) -> VercelBooleanQuestion {
    VercelBooleanQuestion {
        r#type: "boolean",
        instructions: q.instructions.clone(),
        criteria: q.criteria.clone(),  // true/false 字段
    }
}
```

**实测验证**：本仓库 `life-series-benchmark/` 用 Vercel Jev 跑 21/80 篇，partial 准确率 71.4%（vs human baseline）—— 这证明翻译层有效。

## 四、能力收敛（callClampEffort 模式）

借鉴 jev-life 的 `resolveEffort` + `capabilitiesOf` 三态 effort 设计：

```rust
/// 三态 effort → 最终下发的值（或 undefined = 不发）
///
/// - 省略 (omitted) → 用上游默认（"none"，关思维链）
/// - null → 明确要求"不发这个字段"
/// - 具体档位 → 过 capabilitiesOf()，收不了就不发
fn resolve_effort(
    desired: Option<Option<EffortLevel>>,
    upstream: &str,
) -> Option<EffortLevel> {
    match desired {
        None => Some(EffortLevel::None),      // 客户端没意见 → 默认
        Some(None) => None,                  // 显式 null → 不发
        Some(Some(level)) => {
            let cap = capabilities_of(upstream);
            if cap.supports_effort(level) { Some(level) } else { None }
        }
    }
}
```

**为什么是三态而不是两态**：界面"思考强度 = 留空"是用户的**明确选择**（实测与 `none` 同为 3/3），与"客户端没传"必须分开。

## 七、Router 对 capability 的使用

```rust
trait RouterStrategy {
    async fn select_upstream(
        &self,
        req: &DecisionRequest,
        health: &HealthRegistry,
    ) -> Option<UpstreamId>;
}

/// FailoverChain：按 priority 顺序，第一个 capability 匹配 + 健康 = 用
struct FailoverChain {
    fallbacks: Vec<UpstreamId>,
}

impl RouterStrategy for FailoverChain {
    async fn select_upstream(&self, req: &DecisionRequest, health: &HealthRegistry) -> Option<UpstreamId> {
        for id in &self.fallbacks {
            let up = health.get(id);
            // 1. 健康？
            if !up.is_healthy() { continue; }
            // 2. capability 满足？（例如请求里有 noul，上游必须支持 noul 或 boolean）
            if !up.capabilities().supports_question_types(req.question_types()) { continue; }
            return Some(id.clone());
        }
        None
    }
}
```

## 八、capability 与 CORS / 浏览器的关系

- **C1-C2 云端**：浏览器直连被 CORS 拦。Jev-Switch 作为代理（"本地代理"）解决。
- **C3-C5 本地**：浏览器可直连（localhost 不受 CORS 限制）。

Jev-Switch 的桥接模式（详见 `02-` v2.1）让"浏览器 + Jev-Switch + 任一上游"成为默认路径。
