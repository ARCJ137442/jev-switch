# 「Jev-Switch」用户叙事探索

以下用**第一人称叙事**展开，每个叙事代表一类真实用户。不追求覆盖全部可能性，而是通过具体的故事来暴露：谁会在什么场景下需要这个东西，以及他们为什么会觉得“终于有人做了”。


## 叙事一：被 API Key 轮换逼疯的独立开发者

> 我叫陈默，独立开发一个小型客服自动分类 SaaS。我用 Jev 做“这条消息该进哪个队列”的判定，每天大约 12 万次调用。
>
> TypeSafe 官方按输入 token 计费，量大了之后我开始找更便宜的渠道。OpenRouter 上有 Jev 的 decisions 端点，价格便宜 15% 左右，但有速率限制。Vercel AI Gateway 的延迟更低，但按请求计费，小请求不划算。
>
> 我的做法很原始：在 `.env` 里放三个 Key，代码里写一个 `if-else`，根据当前 QPS 选上游。每次改配置要重新部署，每次上游出问题要手动切换。上个月 OpenRouter 抽风了 40 分钟，我坐在电脑前手动把流量切到 TypeSafe，一边切一边骂自己为什么不做个网关。
>
> 我需要的东西很简单：一个本地跑的小服务，监听 `localhost:11435`，我所有代码把 Jev 请求发给它，它在后面根据我写的规则——便宜优先、延迟优先、或者某个上游挂了就自动切——决定发给谁。**我不需要它懂 LLM，不需要它做 Agent，我只需要它当一个聪明的反向代理。**


## 叙事二：在本地和云端之间反复横跳的研究员

> 我是做决策模型对齐的研究员，手上有三台机器：一台 Mac Studio 跑 Laya 做快速实验，一台 A100 服务器跑微调后的 SimpleJev 变体，还有 TypeSafe 官方的 API 用于基线对比。
>
> 我的实验代码本来应该只关心 `predict(state, questions)`，但实际写出来全是 `if backend == "laya": ... elif backend == "simplejev": ... elif backend == "typesafe": ...`。每次加一个新后端，所有实验脚本都要改一遍。
>
> 我想要的是一个**统一接口**：不管后面接的是 421M 的 Laya 还是闭源的 TypeSafe，我的代码只写一次。而且我需要**在同一台机器上同时运行多个后端**，比如把 Laya 和 TypeSafe 的响应做并排对比，看它们在哪些问题上分歧最大。如果有一个 Jev-Switch 跑在本地，我只要把实验代码指向它，然后在它的配置里挂三个后端，切换只需要改一行配置。
>
> **我还想要一种能力：让同一个请求同时发给两个后端，把两个答案都拿回来。** 这在研究场景下很有用——我不是在做生产路由，我是在做模型对比。


## 叙事三：被合规要求锁死在私有化部署的企业团队

> 我在一家金融科技公司做 AI 平台，我们内部有一个用 Jev 格式做的风控决策服务。但合规部门的要求是：**任何数据都不能出内网**。
>
> 这意味着 TypeSafe 官方 API 不能用，OpenRouter 不能用，Vercel 更不能用。我们只能在本地跑开源模型。但问题是，我们的业务逻辑代码是围绕 Jev 的 `state + questions → answers` 写的，如果本地模型不兼容这个格式，所有代码都要重写。
>
> 我们试过 sys1，但它只支持 Laya。我们需要一个**可插拔的本地 Jev 网关**：开发环境接 Laya，测试环境接我们微调的 Decider-2B，生产环境接内部部署的 System-One 4B。所有环境对外暴露同一个 Jev 格式的接口，切换只发生在网关的配置层。
>
> **我们不需要任何云端上游。** 我们需要的是一个纯粹的本地 Jev 路由层，能让我们的业务代码完全不知道后面换了模型。


## 叙事四：从 OpenAI 迁移过来、被 `messages` 搞晕的产品经理

> 我们的产品原来用 GPT-4o 做“这条评论是正面还是负面”的分类。后来发现 Jev 做同样的事成本只有 1/20，而且输出是校准过的概率，可以直接拿来做阈值路由。
>
> 但迁移过程很痛苦。OpenAI 的调用格式是 `messages: [{role: "user", content: "..."}]`，Jev 是 `state: "..."` + `questions: {...}`。我们的代码库里有几十处调用点，每一处都要改。
>
> 我想要的是一个**转接层**：我保持现有的 OpenAI 格式调用不变，但把 `base_url` 指向一个本地服务。这个服务收到 OpenAI 格式的请求后，把它翻译成 Jev 格式，发给 TypeSafe，再把 `answers` 翻译回 OpenAI 的 `choices` 格式。**我不需要它完美——我只需要它把我的分类 prompt 自动转成 Jev 的 `questions`，把 `logprobs` 映射成 Jev 的 `noul` 概率。**
>
> 这样我可以渐进式迁移：先把 10% 的流量切到 Jev-Switch，对比成本和准确率，再决定要不要全量。


## 叙事五：开源模型维护者，想给社区一个“一键接入 Jev 生态”的入口

> 我维护一个开源决策模型，叫 MiniJev，只有 200M 参数，在消费级 GPU 上能跑。我的用户群体是学生和独立开发者，他们没有 TypeSafe 的 API Key，也不想注册 OpenRouter。
>
> 我的模型有自己的 Python API，但用户希望用 Jev 的格式来调用——因为 Jev 生态里的工具（比如 jev-life、jev-2048）都只认 `POST /v1/systemone`。如果我的模型不能暴露这个接口，用户就没法在 Jev 生态里用它。
>
> 我不可能为每个下游工具写一个适配器。我需要一个**标准的 Jev 兼容服务器**，我的模型作为它的一个后端插件接入。用户下载 Jev-Switch，在配置里写上 `backend: "minijev"`，然后所有 Jev 生态的工具都能直接用我的模型。
>
> **对我来说，Jev-Switch 是开源决策模型进入 Jev 生态的“标准入口”。** 没有它，每个模型都要自己写一套兼容层，生态就碎了。


## 叙事六：游戏开发者，想让 NPC 决策在本地和云端之间无缝切换

> 我在做一个 AI 驱动的文字冒险游戏。NPC 的行为决策用 Jev 格式定义：`state` 是当前场景描述，`questions` 包括“NPC 是否愤怒”“NPC 是否信任玩家”“NPC 下一步行动是什么”。
>
> 开发阶段我用 Laya 本地跑，因为迭代快、不花钱。但发布到 Steam 后，玩家的机器性能参差不齐，有些人跑不动本地模型，我需要一个云端回退。同时，我还想让高级玩家可以选择“本地模式”来保护隐私。
>
> 这意味着游戏代码里不能硬编码任何一个后端。我需要一个**运行在玩家本地的 Jev 网关**，游戏进程把决策请求发给 `localhost:11435`，网关根据玩家的设置——本地优先 / 云端优先 / 仅本地 / 仅云端——决定把请求发到哪里。
>
> **如果 Jev-Switch 存在，我的游戏代码只需要写一次。** 玩家换后端不需要我发新版本，只需要改网关的配置。


## 叙事七：成本工程师，用 Jev-Switch 做 A/B 测试和降级策略

> 我的工作是优化公司的 AI 成本。我们每个月在 Jev 调用上花 $8,000，我需要找到在不降低质量的前提下省钱的方法。
>
> 我的策略是：把 90% 的简单请求路由到 Laya（成本接近零），10% 的复杂请求路由到 TypeSafe。但我需要**证据**来证明 Laya 在简单请求上的质量足够好。这意味着我需要在生产流量上做 A/B 测试：同样的请求同时发给 Laya 和 TypeSafe，对比两者的答案差异，统计分歧率。
>
> 如果有一个 Jev-Switch，我可以在它上面挂两个后端，配置“影子模式”：所有请求正常发给 TypeSafe，同时复制一份发给 Laya，把两者的答案都记录到日志里。跑一周后，我拿着数据去找老板说：“看，Laya 在 87% 的请求上和 TypeSafe 一致，我们可以把那些请求切过去了。”
>
> **Jev-Switch 是我做成本实验的基础设施。** 没有它，我只能在代码里写临时的 A/B 逻辑，脏且不可复用。


## 叙事八：Jev 生态的“基础设施派”贡献者

> 我不是最终用户，我是给 Jev 生态写工具的人。我写过 jev-router、jev-classifier、jev-gateway——都是围绕 Jev 做 Agent 集成的。
>
> 我的每一个工具都需要一个“Jev 客户端”来发请求。如果每个工具都自己实现一遍 TypeSafe / OpenRouter / Vercel 的 HTTP 调用，代码重复率极高，而且每个工具都要单独处理“上游挂了怎么办”“Key 怎么管理”“怎么切换”。
>
> 我需要的是一个**共享的 Jev 传输层**：所有 Jev 生态的工具都指向 `localhost:11435`，由 Jev-Switch 统一管理上游连接、重试、降级、Key 轮换。我的工具只需要关心“问什么问题”，不需要关心“问谁”。
>
> **Jev-Switch 是 Jev 生态的“基础设施层”。** 它不做 Agent，不做工具调用，它只做一件事：让“发送 Jev 请求”这件事变得标准化、可配置、可切换。


## 叙事九：隐私敏感的个人用户，把 Jev-Switch 当“数据保险箱”

> 我用 Jev 做日记情感分析。每天写完日记后，我把内容发给 Jev，问“今天的情绪是正面还是负面”“有没有值得警惕的消极信号”。
>
> 但我很不舒服：我的日记内容被发送到了第三方服务器。即使 TypeSafe 承诺不存储数据，我也无法验证。
>
> 我需要的是一个**本地网关**，它能做两件事：第一，对敏感内容做本地预处理（比如用 Laya 在本地做初步判定，只把不确定的部分发给云端）；第二，如果配置为“仅本地”，所有请求都在本地完成，数据永远不出机器。
>
> **Jev-Switch 对我来说是一个隐私边界。** 它让我可以精确控制“哪些数据离开我的机器”，而不是把控制权交给某个 API 提供商。


## 叙事十：教育工作者，用 Jev-Switch 做课堂演示

> 我在大学教 AI 伦理课。我想让学生直观地理解“同一个决策问题，不同模型的答案有什么差异”。
>
> 我准备了一个 Jev 格式的问卷：`state` 是一个伦理困境描述，`questions` 包括“你是否认为这个行为是道德的”“你的置信度是多少”。我让学生用 TypeSafe、Laya、和一个我们微调过的模型分别回答同一个问卷，然后对比三者的答案分布。
>
> 如果没有 Jev-Switch，我需要为每个模型写一套调用代码，课堂上根本没时间做这个。有了 Jev-Switch，我只需要在配置里挂三个后端，然后在界面上做一个切换按钮。学生看到的是：同一个问题，三个后端，三个不同的答案分布。
>
> **Jev-Switch 让“多模型对比”从一个工程任务变成一个教学演示。**


## 叙事聚类：谁在什么场景下最需要它

| 用户类型 | 核心痛点 | Jev-Switch 解决什么 | 使用频率 |
|---|---|---|---|
| **成本优化者** | 单一上游太贵，多上游切换靠手动 | 运行时路由 + A/B 测试 | 每日 |
| **隐私敏感者** | 数据不能出本地 | 本地优先 + 云端回退 | 持续 |
| **研究者** | 多后端对比靠改代码 | 统一接口 + 并行查询 | 每周 |
| **企业合规团队** | 只能私有化部署 | 纯本地多后端路由 | 持续 |
| **开源模型维护者** | 模型进不了 Jev 生态 | 标准 Jev 兼容入口 | 一次性接入 |
| **游戏/应用开发者** | 不能硬编码后端 | 本地网关 + 玩家可配置 | 发布后持续 |
| **生态工具开发者** | 重复实现传输层 | 共享 Jev 传输层 | 持续 |

**最强烈的需求信号来自三类人**：成本优化者（有钱的痛点）、隐私敏感者（有合规的痛点）、生态工具开发者（有重复劳动的痛点）。这三类人的共同特征是：**他们已经在做这件事了，只是做得很脏**——在代码里写 `if-else`、在 `.env` 里手动切换、在脚本里复制粘贴 HTTP 调用。Jev-Switch 对他们的价值不是“新能力”，而是“把已有的脏 workaround 变成干净的基础设施”。

# 「Jev-Switch」用户叙事 Before / After 对照

以下对照延续前一版的十类用户，聚焦同一个问题：**安装 Jev-Switch 前后，他们的工作方式发生了什么具体变化。**


## 叙事一：被 API Key 轮换逼疯的独立开发者

**Before**：陈默的代码里有三个 Key、一个 `if-else`、一个手写的重试循环。OpenRouter 抽风时，他坐在电脑前手动把流量切到 TypeSafe，改 `.env`，重新部署，等 3 分钟。上个月切了四次。

**After**：`localhost:11435` 成了他所有代码里唯一出现的 Jev 地址。OpenRouter 挂了，Jev-Switch 按他配置的“延迟优先”规则在 200ms 内自动切到 TypeSafe。他是在事后看日志才知道切换发生过。**他的代码库从此没有“上游”这个概念。**


## 叙事二：在本地和云端之间反复横跳的研究员

**Before**：实验脚本里全是 `if backend == "laya": ... elif backend == "simplejev": ... elif backend == "typesafe": ...`。每加一个新后端，所有脚本改一遍。想对比两个模型的答案，得写两套调用、手动拼结果。

**After**：脚本里只有 `requests.post("http://localhost:11435/v1/systemone", ...)`。对比 Laya 和 TypeSafe 时，她在 Jev-Switch 配置里加了一段 `mirror: [laya, typesafe]`，同一个请求同时发给两个后端，响应里两个答案并排返回。**她把省下来的时间用来分析分歧，而不是写调用代码。**


## 叙事三：被合规要求锁死在私有化部署的企业团队

**Before**：业务代码是围绕 Jev 格式写的，但本地模型不兼容这个格式。他们试过 sys1，但 sys1 只支持 Laya。开发、测试、生产三套环境用三个不同的调用路径，代码里有三套适配层。

**After**：所有环境指向同一个本地 Jev-Switch。开发环境配置 `backend: laya`，测试环境 `backend: decider-2b`，生产环境 `backend: system-one-4b`。业务代码一行没改。**合规部门看到的是“所有请求都在内网完成”，工程师看到的是“我只需要改一行配置”。**


## 叙事四：从 OpenAI 迁移过来、被 `messages` 搞晕的产品经理

**Before**：几十处调用点，每处都要从 `messages: [{role: "user", content: "..."}]` 改成 `state: "..."` + `questions: {...}`。迁移计划写了三页，排期两周，没人想动。

**After**：他把 `base_url` 从 `api.openai.com` 改成 `localhost:11435/openai-compat`。Jev-Switch 收到 OpenAI 格式的请求，自动把分类 prompt 转成 Jev 的 `questions`，把 `logprobs` 映射成 `noul` 概率。他先把 10% 的流量切过去，对比一周成本和准确率。**迁移从一个“两周的工程”变成了“改一行 base_url 的 A/B 测试”。**


## 叙事五：开源模型维护者，想给社区一个“一键接入 Jev 生态”的入口

**Before**：MiniJev 有自己的 Python API，但 Jev 生态的工具只认 `POST /v1/systemone`。他给 jev-life 写了一个适配器，给 jev-2048 写了另一个，还有第三个工具在排队。每个适配器的代码都差不多，但都得单独维护。

**After**：他在 Jev-Switch 的配置里注册了一个 `backend: "minijev"`，指向自己的模型服务。所有 Jev 生态的工具通过 Jev-Switch 调用 MiniJev，接口格式统一。**他不再为每个下游工具写适配器，而是让工具来适配 Jev-Switch 这一个标准入口。** 生态碎片化的问题，从一个模型维护者的角度被解决了。


## 叙事六：游戏开发者，想让 NPC 决策在本地和云端之间无缝切换

**Before**：游戏代码里硬编码了 Laya 的调用。发布到 Steam 后，低配玩家跑不动本地模型，他只能发一个热修复，加一个云端回退的 `if-else`。高级玩家想要“仅本地模式”保护隐私，他又得加一个开关。每次需求变化，都要发新版本。

**After**：游戏只调用 `localhost:11435`。玩家在设置界面选“本地优先 / 云端优先 / 仅本地 / 仅云端”，Jev-Switch 按配置路由。**他再也不用为后端切换发新版本。** 玩家换后端对他来说是透明的，对玩家来说是可配置的。


## 叙事七：成本工程师，用 Jev-Switch 做 A/B 测试和降级策略

**Before**：他在生产代码里写临时的 A/B 逻辑：`if random() < 0.1: call_laya_async() ; call_typesafe()`。日志格式不统一，分析时要在两个数据源之间手动对齐。这个逻辑脏且不可复用，下一个项目还要重写。

**After**：他在 Jev-Switch 配置里开了 `shadow: { primary: typesafe, shadow: laya }`。所有请求正常发给 TypeSafe，同时复制一份发给 Laya，两个答案自动记录到同一个日志结构里。跑一周后，他拿着“87% 一致率”的数据去找老板。**A/B 测试从“写脏代码”变成了“改配置”。**


## 叙事八：Jev 生态的“基础设施派”贡献者

**Before**：他写的 jev-router、jev-classifier、jev-gateway 每个都自己实现了一遍 TypeSafe / OpenRouter / Vercel 的 HTTP 调用、重试逻辑、Key 管理。三个工具，三套传输层，三个地方要改 Key 轮换策略。

**After**：三个工具都指向 `localhost:11435`。Jev-Switch 统一管理上游连接、重试、降级、Key 轮换。他的工具只关心“问什么问题”，不关心“问谁”。**传输层从“每个工具重复实现”变成了“一个共享的基础设施”。** 他可以把精力放在工具本身的逻辑上。


## 叙事九：隐私敏感的个人用户，把 Jev-Switch 当“数据保险箱”

**Before**：日记内容直接发给 TypeSafe。他无法验证 TypeSafe 是否真的不存储数据。他想过用本地模型，但本地模型的格式不兼容他已有的调用代码，迁移成本太高。

**After**：Jev-Switch 配置为“本地优先”：先用 Laya 在本地做初步判定，置信度高于 0.9 的直接返回，低于 0.9 的才发给 TypeSafe。他可以在日志里看到**每一条数据去了哪里**。配置为“仅本地”时，数据永远不出机器。**隐私从“信任第三方”变成了“可验证的本地配置”。**


## 叙事十：教育工作者，用 Jev-Switch 做课堂演示

**Before**：为了让学生对比三个模型的答案，他需要为每个模型写一套调用代码，课堂上没时间做这个。他只能在幻灯片上展示预先跑好的结果，学生看不到“实时对比”。

**After**：他在 Jev-Switch 上挂了三个后端，在课堂上打开一个简单的 Web 界面，输入同一个伦理困境，点“对比”，三个模型的答案分布并排显示。学生可以自己改问题、自己跑。**“多模型对比”从一个工程任务变成了一个课堂互动。**

| 维度 | Before | After |
|---|---|---|
| **上游切换** | 改 `.env`、重新部署、手动 | 改配置、热重载、自动 |
| **多后端对比** | 写多套调用、手动拼结果 | 一个请求、并行返回 |
| **代码耦合** | 业务代码里全是 `if backend ==` | 业务代码只认 `localhost:11435` |
| **迁移成本** | 改几十处调用点、排期两周 | 改一行 `base_url`、渐进式迁移 |
| **生态接入** | 每个下游写一个适配器 | 一个标准入口、所有工具复用 |
| **隐私控制** | 信任第三方、无法验证 | 本地边界、可验证、可配置 |
| **A/B 测试** | 生产代码里写脏逻辑 | 配置层开 `shadow` 模式 |
| **教学演示** | 预跑结果、静态展示 | 实时对比、学生可交互 |

**核心洞察**：这十类用户 Before 状态的共同特征是**“他们已经在自己解决这个问题了，只是解决得很脏”**。Jev-Switch 的价值不是提供新能力，而是把已有的脏 workaround 变成干净的基础设施。After 状态的共同特征是**“业务代码不再知道后端的存在”**——这才是“Switch”这个词的真正含义：切换发生在业务代码看不见的地方。
