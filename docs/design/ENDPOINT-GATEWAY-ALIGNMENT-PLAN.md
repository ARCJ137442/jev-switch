## 1. 产品本质与边界

**Jev Switch 是在模型调用入口之间进行可配置转换的中间网关，承担入口聚合、自动化、智能化及可视化交互维护。**

最小功能入口是 `API 地址 + 凭据 + 模型 ID`。两侧在调用形式上同构，在软件中的管理职责不同：Jev Switch 向上游调用服务，同时作为提供商向外部提供自己的服务。

```text
外部调用者
    |
    | 网关地址 + 调用 token + 对外模型 ID
    v
+------------------+     +--------------------+     +----------------------+
| 对外入口卡片     |     | 调用路由 DAG       |     | 提供商复合卡片       |
|                  | --> |                    | --> |                      |
| 对外模型 ID      |     | 中间节点与分支连接 |     | 地址 + 账号/API key  |
| 独立配置与策略   |     | 选路与失败处理     |     | 本配置的多个模型端口 |
+------------------+     +--------------------+     +----------------------+
       多个入口                 可交互编辑                  多份接入配置
```

- 轻量、本地与云端兼容、快速配置、高度可集成；性能与界面操作流畅度是持续要求。网关安排和转发调用，推理由上游承担。
- `local/cloud` 不描述上游所在位置。local 仍可访问云服务；云机上的 `127.0.0.1` 指云机自己。调用 token 在本地通常为空，云端按访问管理配置使用。
- 不新增 OpenAI/Anthropic 格式入口。CLI、更多上游类别、完整 OTel、更多桌面平台等按后续路线推进，不能借“所有计划”重启早期全部愿景。
- 后来已批准的提供商管理、入口策略、分 Token 管理及统计专项继续保留；旧冻结清单不能覆盖后续明确授权。
- 当前智能化是在既定规则内自动选路和处理故障，不自主改写长期配置。用户提出的“利用自身 Jev 服务调整自身”仅保留为未来方向，本阶段不实施。

## 2. 两侧入口与卡片的严格分工

| 对象 | 定义与职责 | 界面表现 |
|---|---|---|
| 提供商接入配置 | 一份具体地址、账号/凭据配置及其可用模型集合；账号可用命名配置表达，不要求上游支持用户名登录 | 一份接入配置一张提供商复合卡片 |
| 上游模型调用入口 | 选定某份接入配置下的一个模型；执行时确定完整三元组 | 提供商复合卡片内的模型端口 |
| 对外模型调用入口 | Jev Switch 提供的一项模型服务；内部独立配置路由集合与策略 | 对外入口卡片；配置、启停、编辑、删除和复制标识 |
| 中间路由节点与边 | 连接入口与上游资源，表达多跳、分支、候选及失败处理 | 从左到右的可编辑调用路由 DAG |

### 2.1 提供商复合卡片

用户明确选择：**一份接入配置一张卡**。

```text
同一服务地址
  +-- 提供商卡片 A·个人：个人账号/key -> 模型 M1、M2
  +-- 提供商卡片 A·团队：团队账号/key -> 模型 M1、M3
```

两个账号可使用同一地址与提供商类型，各自维护模型资源；卡片内多个模型复用该账号/key。不能因为地址相同就合并两套凭据，也不能因为模型不同就要求复制同一份凭据。UI 可使用“服务名·个人/团队”等名称区分配置。

提供商管理参考 CC Switch，在网关中的职责类似 sub2api 的账号管理。这里明确的是产品职责和卡片粒度，尚未声称已研究或照搬其最新实现。

模型集合属于对应账号/凭据的资源上下文。自动发现、手动维护与刷新失败时的交互，需要按上游实际能力补充契约；**本轮没有决定所有上游都具备模型发现 API**。修改凭据后必须重新核对模型可用性与既有路由引用，不能悄悄套用另一账号的资源状态。

### 2.2 对外入口卡片

对调用者而言，入口是 `网关地址 + 调用 token + 对外模型 ID`；对内部管理而言，它是有独立配置的服务入口。

- 对外模型 ID 和内部入口 ID 可使用相同值，例如 `jev-stable`；不因称谓不同而强制新增另一套业务标识。
- 一个对外入口可以指向多个上游；一个上游入口也可以被多个对外入口复用。
- 对外模型集合来自创建的对外入口，不能直接把所有上游模型当成已发布的服务。
- 不同调用 token 访问同一对外入口时共享其路由规则。Token 用于访问权限与调用归属，**本轮不引入按 token 覆盖同一入口路由的机制**。
- 调用 token 与上游 key 属于不同信任边界；上游密钥留在 daemon，前端使用配置引用和脱敏信息。

例如 `jev-fast` 与 `jev-stable` 都可以复用 `A·个人/M1`。前者与后者各有策略，后者还可以增加 `B·团队/M2` 作为兜底。修改其中一个对外入口的策略，不应隐式修改另一个入口的独立配置。

### 2.3 路由图是产品核心工作台

用户确认的最终形态是：**左侧对外入口卡片 → 中间调用路由 DAG → 右侧提供商复合卡片内的模型端口**。

图必须可快速、直观地查看和修改节点、连线与属性，支持中间节点、多跳和分支。继承已批准的双端拖拽/重连、端口反馈、磁吸、选中与删除、撤销/重做等交互；保存、刷新、执行与图中状态应一致。

简单直连是 DAG 的特例。旧二部图不能作为最终图形能力的上限。环路和失效引用必须可识别，编辑失败要有明确反馈；撤销应恢复完整路由属性，而不只是重新画一根线。健康、流量、实际命中路径和错误必须有真实数据来源。

### P1：统一配置关系与契约

- 同步提供商配置 ID、上游模型端口、对外入口、路由节点/边及策略的关联，保留账号凭据复用和对外入口独立配置。
- 明确持久化的权威来源、TOML/SQLite 迁移与兼容读取方式、内存快照更新及失败回滚，避免两套配置各自宣称有效。
- 对外入口复用既有内存 + SQLite、修改后下一请求生效的方向。存储/API 草图应按新概念修订，不能机械套用历史 schema。
- 补齐直接上游测试的管理权限与后端契约。`/v1/models` 和 `/v1/systemone` 可用于对外入口路径，不能据此宣称直接上游测试已存在。

**验收：**用同地址两账号、多模型、两对外入口复用上游的例子，能无歧义地表达、保存、恢复与调用；协议与权限边界明确。

### P2：打通提供商、对外入口与策略执行

- 提供商配置可动态管理，变更后运行适配器使用正确地址/凭据；不局限于启动时硬编码的两项实例。
- 对外入口 CRUD、启停、重命名及路由关联在持久化、运行时和查询结果间一致。禁用或删除不能只改数据库而仍继续执行旧路由。
- 已批准策略范围保留 `failover / race / load_balance / shadow`，默认 failover；入口可跟随全局或指定策略。先用 failover 打通闭环，再逐项完成其他策略，不以施工顺序删减范围。
- 在契约中明确 priority 与权重的含义、race 有效胜出/取消、shadow 生命周期和计量；未接通执行的配置不得在 UI 中显示为已可用。
- 请求事件、实际路径、失败与回退记录接入日志/SSE/统计；按已批准 Token 管理范围隔离访问与调用记录。

**验收：**API 修改后下一请求按新配置执行；失败更新不留下半套状态；重启恢复一致；策略用受控上游做请求级验证，而非仅检查 API 200。

### P3：入口配置、交互 DAG 与多语言

- 提供商页采用复合卡片；Routing 中落实可发现的“入口”配置项与对外入口卡片，沿用已批准 tab 方案起步，不擅自另起导航重构。
- 左对外入口、中间路由节点、右提供商模型端口；图形编辑与配置表单共享同一真实状态。
- 完成节点/连线增删、拖动、双端重连、属性编辑、磁吸反馈、撤销/重做与环检测。输入框编辑时不能被全局 Delete 等快捷键误伤。
- 多语言用可扩展的语言列表；本轮完整覆盖现有中文/英文流程，为日语、俄语、法语等留出正常扩展机制。实施时核对 CC Switch 的语言选择、词条组织和回退方式；不把尚未翻译的语言列成可用。
- 按 §3.2 调整首窗及全应用响应式布局；导航、身份状态、弹窗底部操作和滚动边界必须在窄/矮视口中可用。

**验收：**真实操作可以创建入口并配置多跳/分支；刷新与重启后图不漂移；撤销恢复完整属性；中文/英文均能完整操作，新增语言无需重写切换按钮逻辑。

### P4：两类入口横向比较

- 同时支持对外入口、直接上游入口，以及两类明确标注的混合比较；共享同一份输入快照。
- 对外入口完整经过自身路由策略；上游入口直接绑定指定接入配置与模型，不隐式借用同名对外入口，也不向浏览器下发上游密钥。
- 每个目标独立处理运行、成功、失败、取消、重试；迟到响应不能覆盖新一轮结果。某列失败不抹除其他列成功结果。
- 宽屏充分利用可用空间呈现输入、目标与并排结果；窄屏可顺序阅读操作，避免保留无内容的大块侧栏。

**验收：**对外-对外、上游-上游、对外-上游三组比较均可操作；相同模型名但不同账号不会混淆；直接上游与入口策略的差异可解释。详见 [演练场比较专项](PLAYGROUND-COMPARISON-PLAN.md)。

### Jeview 可借鉴的交互与边界

Jeview 的主视图不是普通日志表：中心画布实时呈现 Jev、问题、答案及概率；若后续调用携带前一回答的 event ID，就从该答案长出分支。旁侧近期调用列表用人类可读的问题/答案和相对时间做摘要；选中一条后，抽屉按题目结构化呈现结果，模型、状态、耗时、usage、事件 ID 等放入详情区，原始请求/响应 JSON 默认收在次级折叠区。它还提供 run 分组、跨历史搜索、问题统计和画布布局控制。

| Jeview 模式 | Jev Switch 的适配方向 | 当前差距/边界 |
|---|---|---|
| 最近调用列表：状态、短摘要、时间 | 保留现有紧凑活动行；让请求 ID、入口、结果状态、上游路径、耗时、usage、调用次数一眼可扫 | 当前已有 50 条实时活动和这些基础摘要，原始 JSON 默认折叠；尚无活动筛选和历史搜索 |
| 单条记录的结构化详情抽屉 | 用实际持久化的 route trace 展开“请求入口 → 路由策略 → 已尝试 hop（顺序/结果/耗时/是否重试）→ 最终上游 → 响应 usage/结果”；错误时明确说明停止原因 | 当前摘要多显示 provider → model，未把每个 route hop 做成逐步过程；无持久字段就显示“未记录”，不推测路径 |
| event ID 串成调用因果图 | 以稳定 request ID 关联同一次请求的 history、SSE 与响应；在详情中显示真实的路由 DAG 子路径。仅当未来协议确有父子请求 ID 时再画跨请求树 | Jev Switch 的 DAG 表示“配置路由”，Jeview 的图表示“问题触发后续问题”，两者语义不同；不能把静态配置图误当成此次实际执行记录 |
| run 选择、搜索和统计 | 筛选/搜索 request ID、时间、调用 token/调用者、公开入口、provider/model、成功/失败；统计可按入口/provider 聚合成功率、耗时与真实报告成本 | 目前事件页显示最近记录并可实时更新；费用未知仍要显示“未知”，不能自行估价 |
| 题目/答案概率分布图 | 只在历史 API 明确保留类型化答案字段且数据边界评估通过后，考虑把 Jev 的 Choice/Score/Noul 答案做可读摘要 | 当前调用历史主要保留安全元数据与 route trace，不应为模仿视觉而保存原始 state/prompt 或整份请求体 |

借鉴重点是“摘要先读、详情分层、真实路径可追、搜索能定位”，不照搬整屏全局语义图。对于 Jev Switch，列表/时间线比常驻大画布更适合作为默认历史视图；宽屏详情可再展示 route DAG 的本次实际路径，窄窗切为纵向步骤列表。若答案正文以后进入历史记录，必须先定义字段白名单、保留期限、调用者可见范围与明确的数据保留提示。

Jeview 明确把每次完整请求和响应、以及明文 TypeSafe key 存入本地 SQLite，监听 127.0.0.1 且无登录，README 也警告不要暴露到公网。**这些存储和认证选择仅是对方项目的设计，不作为 Jev Switch 的实现模板。**Jeview 值得借鉴的是可视化、分层披露和追踪交互；Jev Switch 继续遵循不保存 prompt/request body 和上游密钥、只展示可审计安全 trace 的边界。
