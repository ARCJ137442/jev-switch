## 一、战略定位（一句话 + 双态模型）

> **集 CC Switch 与 sub2api 为一身：本地可路由，云端可中转。**

```
                    ┌─────────────── 内核（同一个，只换 mode）───────────────┐
   调用方           │  mode = local │ mode = cloud                          │
  ┌──────┐          │  免 token      │  /v1: Bearer 调用 token               │
  │本地工具├────────►│  LAN 直连      │  admin: 独立可设置登录密码            │
  │CLI/UI │          │  (CC Switch /  │  (sub2api / newapi 式中转站)         │
  └──────┘          │   LM Studio)   │  聚合 官方/Vercel/… = 一个 Jev API    │
                    └───────┬────────┴──────────────┬──────────────────────┘
                            │                       │
              上游地址解析 = 以内核所在位置为准（不区分云端/本地拓扑）：
              内核 LAN 恰有 Laya 等本地服务 → 自然直连；没有 → 配什么地址连什么
```

**拓扑不区分原则（用户裁决，必须写进部署文档）**：`mode` 开关**只管鉴权**，完全不涉及上游拓扑。「云端环境/PC环境」不做区分——内核访问 HTTP 地址一律以内核所在的位置来访问；云机同 LAN 有 Laya 就直连，没有就没有。

**云端中转的价值锚（用户原话）**：对「自定义 TypeSafe Jev 兼容 HTTP 提供商」至关重要——把官方、Vercel 等处的服务中转聚合**变成一个 API 形式**。

## 四、三线作战（任务 #42 / #43 / #44）

### 线 1 · Docker 云部署（#43）——先行，今晚"可玩"核心
- **双态开关**：配置 `mode = local | cloud`；local=现状免 token；cloud=`/v1` 校验 Bearer 调用 token、admin 校验独立登录密码（均可配置）；**不区分上游拓扑**（§一 原则写进部署文档）
- **交付物**：`Dockerfile`（daemon + 前端 dist 同机托管，nginx 或 daemon 直托管二选一在任务书中定）、`docker-compose.yml` 单命令、部署文档（含云态鉴权风险块与拓扑不区分说明）
- **验收**：compose 一条命令起；cloud 态无 token→401 / 有 token→200；admin 密码门生效；local 态回归免 token；三服务冒烟复跑
  > **落地注（2026-09-23）**：#43 已落地 —— mode 双态 + cloud 双 token 鉴权（login→内存会话，二选一取标准形态）+ ServeDir 同源托管 + compose/deployment.md；契约 0.0.0.0 绑定偏差已备案 `docs/deployment.md` §五。
  > **落地注二（2026-09-23）**：mode 热切已落地 —— `PUT /v1/admin/mode` 运行时翻转（含激活原子设密）+ `PUT /v1/admin/listen` 热 Rebind（ListenSupervisor 任务级小网关，零进程重启），细则 `docs/deployment.md` §九。
