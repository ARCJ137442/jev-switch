## 二、核心旅程地图

### 旅程 1：5 分钟快速启动（Alex 的第一天）

**场景**: Alex 克隆了仓库，想快速测试 Jev-Switch

#### 步骤

1. **启动后端**（2 分钟）
```bash
# 使用示例配置
export JEV_SWITCH_CONFIG=rs/providers.example.toml
cargo run --manifest-path rs/Cargo.toml
# → 监听 127.0.0.1:11435
```

2. **打开前端**（1 分钟）
```
浏览器访问 http://127.0.0.1:11435
自动加载内置 UI（ui/dist）
```

3. **查看 Dashboard**（1 分钟）
   - 看到 2 个 provider（laya, vercel）
   - 看到 8 条路由配置
   - mode=local（本地模式，无需密码）

4. **测试 Playground**（1 分钟）
   - 选择 model: `jev`
   - 输入一个 Choice 问题
   - 点击 "Run Jev"，看到路由到 vercel

**结果**: ✅ 5 分钟内完成首次调用，零配置门槛

### 旅程 2：配置自己的上游（Alex 的第二天）

**场景**: Alex 想添加自己的 Vercel API key

#### 步骤

1. **进入 Providers 页面**
   - 点击 vercel 卡片的 "Replace key"
   - 粘贴 `VERCEL_TOKEN`
   - 点击 "Probe" 测试连通性

2. **添加新路由**
   - 进入 Routing 页面
   - 从左侧 `my-model` 拖出箭头
   - 连接到右侧 vercel 的 `typesafe-ai/jev` 端口
   - 保存

3. **验证路由**
   - Playground 选择 `my-model`
   - Run Jev，看到请求成功

**关键交互**: 电路板拖拽建边，直观易懂

---

### 旅程 3：切换到团队模式（Morgan 的部署日）

**场景**: Morgan 要把 Jev-Switch 部署到云端，给团队 5 人使用

#### 步骤

1. **切换 mode**
   - Dashboard 点击 "Switch to cloud mode"
   - 设置 admin 密码（首次激活）
   - 自动 rebind 到 `0.0.0.0:11435`

2. **生成调用 token**
   - Admin 面板 → Tokens
   - 创建 3 个 token（dev/staging/prod）
   - 分发给团队成员

3. **配置 failover**
   - Routing 页面
   - 设置 `jev` 模型的 priority：
     - vercel (priority=10, sticky=session)
     - laya (priority=30, on_error=next)
   - 第一次调用命中 vercel，失败后自动 failover 到 laya

**关键价值**: 一键切换本地/云端，零重启

---

### 旅程 4：实时监控与诊断（Taylor 的运维日）

**场景**: 生产环境 vercel 偶尔超时，Taylor 需要快速定位

#### 步骤

1. **Dashboard 实时流水**
   - 看到最近 50 条请求
   - 发现多条 `error: upstream timeout (vercel)`
   - 自动 failover 到 laya

2. **Providers 健康检查**
   - vercel 显示红灯（498ms → timeout）
   - laya 绿灯（1ms 正常）

3. **调整路由权重**
   - Routing 页面
   - 临时降低 vercel priority
   - 观察流水，确认流量切到 laya

**关键价值**: 实时可观测性，快速响应故障

## 三、关键交互细节

### 电路板焊接隐喻（Routing 页面）

**设计语言**: 
- 左侧 = API 调用点（焊点）
- 右侧 = 上游出口点（焊点）
- 箭头 = 电路连线（单向流动）

**操作流程**:
1. 点击左侧 model 端口，拖出箭头
2. 悬停到右侧 provider 内部模型端口
3. 箭头吸附（磁吸效果），释放鼠标完成连接
4. 自动保存到配置文件

**视觉反馈**:
- 拖拽时：虚线预览
- 命中端口：高亮 + 磁吸
- 完成连接：实线箭头 + priority 标签

---

### 热模式切换（Dashboard）

**操作路径**: Dashboard → mode 卡片 → "Switch to cloud"

**系统行为**:
1. 弹出密码确认框（首次激活）
2. 写入配置文件 `mode = "cloud"`
3. 更新 AuthState RwLock（内存态）
4. 触发 ListenSupervisor 热 Rebind（0.0.0.0:11435）
5. **零进程重启**，在途请求不中断

**用户感知**: 3 秒内完成切换，Dashboard 显示新 mode

---

### Provider 探测（Providers 页面）

**触发**: 点击 "Probe" 按钮

**后端行为**:
```rust
POST /v1/admin/providers/{id}/probe
→ 发送测试 Jev 请求到上游
→ 测量延迟（latency_ms）
→ 返回 {ok, latency_ms, status, error}
```

**前端反馈**:
- 探测中：按钮 spinner
- 成功：绿灯 + 延迟数字（1ms）
- 失败：红灯 + 错误信息（已脱敏）

## 四、典型问题与解决方案

### Q1: 如何快速测试 failover？

**方案**: Playground 页面
1. 选择配置了 failover 的 model（如 `jev`）
2. 故意关闭 priority=10 的上游（vercel）
3. Run Jev，观察 Dashboard 流水
4. 看到 "failover: vercel → laya"

---

### Q2: 本地模式下如何保护配置文件？

**方案**: 配置文件权限（Unix）
```bash
chmod 600 rs/providers.example.toml
```
启动时 daemon 会检查并告警（Windows 降级 warning）

---

### Q3: 如何在生产环境部署？

**方案**: Docker + cloud mode
```bash
docker build -t jev-switch .
docker run -d -p 11435:11435 \
  -e JEV_SWITCH_MODE=cloud \
  -e ADMIN_PASSWORD=<secret> \
  jev-switch
```

配置文件挂载到 `/app/config.toml`

## 五、进阶场景

### 场景 1：多级 failover 链

**需求**: vercel → laya → 本地模型

**实现**: Routing 页面配置 3 条路由
```
jev → vercel (priority=10, on_error=next)
jev → laya (priority=20, on_error=next)
jev → local-model (priority=30, on_error=fail)
```

**行为**: 按 priority 递增顺序尝试，直到成功或全失败

---

### 场景 2：基于 model 前缀的路由

**需求**: `local/*` 模型全部路由到 laya

**实现**: Routing 页面配置 prefix 路由
```
left: local/*
match: prefix
right: laya
upstream_model: null (透传)
```

**行为**: `local/jev` → laya `/v1/systemone` (model=local/jev)

---

### 场景 3：Session sticky（同一会话钉死上游）

**需求**: 用户首次调用选中 vercel 后，后续调用保持在 vercel

**实现**: Routing 配置
```
jev → vercel (priority=10, sticky=session)
jev → laya (priority=20)
```

**行为**: 首次随机选中后，后续通过 session cookie 钉死

## 七、路线图中的未来用户旅程（提案，尚未实现）

以下场景把路线图转换成用户能感受到的前后变化。它们是方向描述，不是当前功能说明或交付承诺。

### 旅程 1：下载一个文件就开始本地试用

Alex 从 GitHub 下载 standalone 独立版，不用先判断安装器类型，也不用解压文件夹。他双击唯一的 exe，应用检查随包资源后启动完整 UI 与本地 daemon；第一次启动耗时、缓存或权限问题都有明确状态。应用数据仍存放在单独目录，用户可以在 exe 邻近目录和系统用户数据目录之间选择。若单文件打包方案无法安全可靠地封装 Tauri sidecar 与资源，产品会如实说明并提供可行的其他发行形态，不把多文件包称作独立版。

**用户得到的变化**：从“先安装/解压/找 daemon，再开始配置”缩成“下载、双击、连接本机地址”。

### 旅程 2：把配置和历史放在自己选的位置

Morgan 把 Jev-Switch 放在项目盘的工作目录里，希望换电脑时能连同配置一起迁移；另一位用户更愿意让数据留在自己的系统用户目录。两人都能在设置中看见当前数据目录与目标目录。切换位置前，Jev-Switch 会说明将迁移哪些配置和历史，复制后核对 SQLite 与运行配置，再确认使用新路径；空间不足或校验失败时仍从旧目录启动，数据不会悄悄变成一份空白。

**用户得到的变化**：数据位置从隐式规则变成可见、可迁移、可核验的选择；程序文件和用户数据分开管理。

### 旅程 3：找到已有的本地或云端 Jev 服务

Alex 记得家里机器和测试云主机上可能已经跑着 Jev 服务，但不记得各自端口。她只选择自己有权检查的主机或网段，Jev-Switch 逐步列出端口响应、协议兼容性、模型清单和鉴权要求；这一步不发起推理。Alex 选中一项后可以主动做带费用提示的模型测试，确认地址和凭据后再快速添加为提供商。未选中的网络范围不会被扫描，扫描结果也不会自动改配置。

**用户得到的变化**：从猜端口、抄 API 地址，变为先看证据和在线状态，再由自己决定测试与接入。

### 旅程 4：让 Jev 帮忙判断路由，但保留决定权

Morgan 给入口写下“客服分类，稳定优先”，并在提供商备注“本地 Laya：适合敏感测试；Vercel：覆盖广”。他选择本地 Laya 作为决策模型，询问“这个提供商值得链接到这个入口吗？”Jev 根据这些备注与明确标注的历史案例，列出推荐、理由、置信度和还需验证的点；Morgan 可以接受、改写或拒绝，并能撤销已应用建议。积累足量标注后，团队再用离线回放检验建议质量，之后才讨论是否允许少数低风险规则自动生效。

**用户得到的变化**：团队经验不再只存在于某个人的记忆里；Jev 先成为有证据的路由顾问，只有经过验证和用户单独授权后，才逐步扩大自治范围。

## 八、其他路线图方向的用户旅程（提案，尚未实现）

### 旅程 5：把熟悉的官方服务直接接进来

Sam 使用 TypeSafe 官方服务，也有 OpenRouter 账号。他打开“供应商”，发现不用再把这些账号先绕到 Vercel 或手写一层兼容服务：选择对应适配器、填写凭据后可以先探测模型，再把某个模型接到自己的对外入口。测试结果会区分适配器不支持的能力、账号鉴权失败和上游暂时不可用；请求依然由所选上游承担，而敏感密钥留在 daemon。

**用户得到的变化**：从“我的账号无法直接接入，得先找额外转接层”变成“选已有适配器即可验证并配置”，同时能提前看清不同服务的能力边界。

### 旅程 6：便携包能自己确认后台服务就绪

Alex 解压便携包后双击正式程序。窗口先核对同目录 daemon 的版本与身份；如果已有可信服务就复用，没有运行才启动并等待健康握手。假如配套文件被误删，界面会指出缺失文件和修复办法，不会只留一个看似正常但无法调用的空窗口。

**用户得到的变化**：从“猜后台该启动哪个 exe、窗口为何连不上”变成“桌面程序负责确认正确 daemon 在运行，并把错误解释清楚”。

### 旅程 7：第一次启动有人带路，重复打开也不添乱

Riley 首次启动时看到一次性引导，按顺序了解网关地址、入口、供应商、调用 Token 和请求会发往哪里；引导完成后自动关闭启动提示，以后仍可手动重开。若默认端口被占用，程序会解释冲突并显示经用户确认后的实际地址；若单例模式开启，重复点击快捷方式会唤回已有窗口。需要并行调试时，Riley 可显式关闭单例并为实例使用不同端口和数据目录。

**用户得到的变化**：第一次不再面对概念堆叠自行摸索；日常启动不再意外生成多个状态不明的实例，端口改变也不会悄悄发生。

### 旅程 8：沿真实调用看见路由，并快速到达常用动作

Morgan 在路由图里等待一笔真实请求通过：入口到上游的实际连线短暂高亮，成功、失败和重试各有易辨认且可关闭的反馈。查看活动记录时，他能分清网关自身选择路由的耗时与上游响应耗时；需要复现时，点“复制 curl”即可得到当前地址与所选入口的命令。按下命令面板快捷键后，他输入“添加入口”或“路由图”，即可跳转或执行匹配动作，不必离开当前页面翻找菜单。

**用户得到的变化**：从依靠静态图和手抄命令猜调用发生了什么，变成能追踪真实路径、分辨耗时来源，并用键盘快速复现或导航。

### 旅程 9：界面和快捷信息按自己的工作环境调整

Jordan 白天在明亮办公室使用浅色主题，晚上改为深色；另一位需要减少动画的用户关闭非必要动效。两人都能用图标和文字标签快速扫状态，但不会因花哨动画漏掉失败信息。在本地模式复制的是当前本机网关地址；云端部署者填好公开 API 地址后则复制该地址，并可单独复制网关调用 Token，不会把供应商密钥混进命令。

**用户得到的变化**：从“界面只能按一种亮度和节奏工作、复制地址还得猜部署位置”变成显示偏好、动效强度和实际调用地址都清楚可控。

### 旅程 10：先看到真实主页，再判断是否适合自己的设备

新用户从仓库链接进入 GitHub Pages 首页，几屏内看到用途、真实截图、快速开始、下载和限制；手机上也能找到文档。想在 Android 使用的人可以先看到可行性结论：哪些桌面能力可复用、哪些后台服务或凭据限制仍未解决。维护者则按可复现的启动、探测、路由、数据库查询和首屏基线查看性能变化；每一轮更改遵循明确边界和恢复办法，不把“快”当成未经测量的口号。

**用户得到的变化**：从进入仓库后自行拼凑用途和支持范围，变成能快速判断适用性；移动端及性能承诺也由实测门槛支撑，而不是先被宣传为已经支持。
